# Releasing CapsNumber

Notes for the maintainer. Users never need this.

## First time: put the project on GitHub

```bash
git init
git add .
git commit -m "CapsNumber 1.0"
gh repo create benoit-zwartjes/CapsNumber --public --source=. --push
```

## Publish a release

The install line downloads `CapsNumber.app.zip` from the **latest GitHub
release**, so there must be at least one release. Pushing a version tag builds
it on GitHub (see `.github/workflows/release.yml`):

```bash
git tag v1.0.0
git push origin v1.0.0
```

After a minute the release appears under
https://github.com/benoit-zwartjes/CapsNumber/releases and the install line works.

To release from your own Mac instead of GitHub Actions:

```bash
./build.sh
ditto -c -k --keepParent build/CapsNumber.app CapsNumber.app.zip
gh release create v1.0.0 CapsNumber.app.zip --title "CapsNumber v1.0.0" --generate-notes
```

## Shipping a change

1. Edit `Sources/main.swift`, run `./build.sh` and the `--self-test`.
2. Commit, bump the tag (`v1.0.1`), push the tag. A new release is built and
   the install line picks it up automatically.

## Icon

`Resources/AppIcon.icns` is generated by `Resources/make-icon.swift` and committed,
so builds and CI just copy it. To change the artwork, edit the script and run:

```bash
swift Resources/make-icon.swift
```

## Signing

Releases are ad-hoc signed, which is enough because the installer fetches the
zip with `curl` (no quarantine flag) and strips quarantine anyway. The trade-off
is that every new build has a new signature, so macOS forgets the Accessibility
approval on update. The installer compares the code hash of the old and new app
and, when they differ, runs `tccutil reset Accessibility be.benoit.CapsNumber` so
users get a clean prompt instead of a silently broken toggle.

If you ever want people to download the zip from a browser and double-click
it without warnings, you need an Apple Developer ID (99 USD per year) and to
notarize the app. Not needed for the terminal install line.
